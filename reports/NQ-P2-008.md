# NQ-P2-008 内容举报、管理员审核与社区排序修复报告

日期：2026-09-28
状态：已完成，等待用户验收

## 问题与验收标准

社区此前没有统一举报入口和处置记录。用户只能依赖管理员直接删除，无法留下举报人、目标身份、原因和处置依据；论坛仅按时间排列，评论量未展示，浏览次数可通过刷新反复增加。目标是建立受控审核链路，并提供服务端排序：

1. 登录用户可以举报策略、帖子和评论，不能举报自己的内容；
2. 原因必填，补充说明限长，服务端 schema 拒绝未知字段和非法枚举；
3. 同一用户对同一目标只能有一条待处理举报，重复及竞争请求不能产生多条；
4. 只有管理员可以读取和处置举报；确认违规必须填写至少 5 字的依据；
5. 举报不会直接删除内容，管理员确认后才隐藏，驳回保持可见；
6. 条件更新和事务保证重复处置只有一次改变状态；
7. 论坛支持最新、热门、讨论最多三种服务端排序；
8. 热度由去重浏览、可见评论、置顶权重和时间衰减计算，客户端不能提交热度；
9. 举报写入和管理员操作受 Session、RBAC、CSRF、分层限流与签名审计保护；
10. 完成隔离数据库测试、Lint、生产构建、数据库完整性检查和 Git 提交。

## 热度规则

服务端计算：

```text
hot_score = (去重浏览量 + 可见评论数 × 5 + 置顶 × 100)
            / max(2, 帖子年龄小时数 + 2)
```

只有数据库中的浏览事件、可见评论和管理员置顶参与计算。请求参数只能选择排序模式，不能写入浏览量、评论数或热度值。前端在“热门”模式下显示该规则的简要说明。

## 残余边界

- `target_id` 属于多态目标，SQLite 不能对三张目标表同时声明外键；目标存在性在立即事务中由硬编码表映射检查，目标类型不能由请求构造表名。
- 管理员确认采用隐藏而非物理删除，便于复核与审计；当前界面尚未提供恢复已隐藏内容的二次申诉功能。
- `post_view_events` 会随访问增长，后续正式迁移/维护框架 NQ-P1-010 应加入过期浏览事件清理作业。
- 真实资金能力保持关闭，本任务没有改变支付、结算或提现上线状态。
