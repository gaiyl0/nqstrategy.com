# NQ-P1-009 不可变钱包账本与余额对账修复报告

复核日期：2026-09-27

## 问题与验收标准

修复前 `users.balance` 是唯一余额事实。提现申请、驳回退款和管理员手工调账直接修改该字段，没有永久流水、变更前后余额、业务引用或独立幂等记录。数据库被重复调用、代码路径遗漏或人工 SQL 修改后，无法证明余额来源，也无法稳定发现多扣、多退和账实不符。

本项验收标准：

1. 每次余额变化必须产生带 `user_id`、金额、前后余额、业务单号和操作者的流水。
2. 提现冻结、驳回退款和管理员调账必须与余额更新处于同一原子事务。
3. 相同业务键或审批重放不能再次改变余额；同一订单/提现同类流水只能存在一次。
4. 普通数据库写入不能绕过账本直接改余额，也不能修改或删除历史流水。
5. 能验证流水签名、hash 链、金额方程和 `users.balance` 最终余额，并能发现篡改。
6. 现有余额迁移后账实一致；生产缺少账本密钥时构建或启动失败。

## 数据结构与不变量

流水类型为 `OPENING_BALANCE`、`EA_SALE`、`WITHDRAWAL_HOLD`、`WITHDRAWAL_REFUND`、`ADMIN_ADJUSTMENT`。金额统一使用整数分，避免浮点金额进入签名和对账逻辑。

每条流水满足：

```text
balance_before_minor + amount_minor = balance_after_minor
previous_hash = 同一用户上一条 entry_hash
users.balance × 100 = 同一用户最后一条 balance_after_minor
```

`business_key` 全局唯一，`idempotency_key` 在提供时全局唯一；同一 `withdrawal_id + transaction_type` 或 `order_id + transaction_type` 只能有一条流水。提现申请的扣款和记录插入任一步失败都会整体回滚。两个并发审批只有条件更新胜出者能追加退款。

## 写保护与篡改检测

SQLite 触发器默认拒绝：

- 非零初始余额绕过账本创建；
- 直接更新 `users.balance`；
- 直接插入账本；
- 更新或删除历史账本。

合法余额更新和流水追加只在进程内受控维护区、同一数据库事务执行。HMAC key ID 支持密钥轮换；历史密钥通过 `LEDGER_INTEGRITY_PREVIOUS_SECRETS` 继续验证。测试分别修改流水金额和用户余额，校验器均报告失败；恢复原值后重新通过。
