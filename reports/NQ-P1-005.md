# NQ-P1-005 审计日志完整性与保留机制修复报告

复核日期：2026-09-26

## 问题与结论

原有 `audit_logs` 是普通 SQLite 表。拥有数据库写权限的进程可以修改、删除或插入记录，应用无法发现；固定 180 天清理会直接删除历史，缺少可验证归档；写入失败只输出控制台，管理员不能查询审计子系统是否退化。

本项已完成本地完整性基线：每条记录使用前一条哈希和独立密钥生成 HMAC，链头另行签名；普通 SQL 无权增删改审计记录、链头和归档历史；过期数据只能由维护命令归档，JSONL 内容、清单和数据库归档批次相互校验并延续原链；管理员读取前会验证链，失败返回 503；响应头暴露本次审计写入是否退化。

生产环境仍必须把归档复制到具有对象锁或 WORM 能力的外部存储。本地 HMAC 能发现不知道密钥的篡改，不能抵御同时控制数据库、文件和签名密钥的主机管理员。

## 数据、密钥和回滚

修改前数据库备份：`backups/data-before-p1-audit-integrity-20260926.db`。开发完整性密钥保存在被 Git 忽略的 `storage/secrets/audit-integrity.key`，不得提交或在报告中披露；必须与数据库备份分开安全备份。

回退必须同时处理代码、数据库和密钥。只回退代码会让旧代码绕过新的签名追加；只恢复数据库会让链头、实时行和归档批次不一致。恢复后必须先执行 `npm run audit:verify`，验证通过才可接收流量。

## 后续边界

1. 部署时将当前开发密钥安全迁入生产密钥管理，或将它暂列入 `AUDIT_INTEGRITY_PREVIOUS_SECRETS`，再用新主密钥签署后续记录。旧签名仍在保留期内时不能删除旧密钥。
2. 配置定时 `audit:archive` 和 `audit:verify`，将非零退出、503 及 `X-Audit-Status: degraded` 接入告警。
3. 将归档文件复制到外部对象锁/WORM 存储；本项目无法在本机代码层替代独立信任域。
