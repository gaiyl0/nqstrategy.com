# NQ-P0-010 审批条件更新与幂等控制报告

完成日期：2026-09-22  
结论：**已完成并通过验收**

## 任务目标

为订单和提现审批建立数据库条件更新、业务唯一约束和持久化幂等键，保证并发或重复请求最多只有一个请求改变状态，退款或结算副作用最多执行一次。

## 幂等协议

订单和提现 PATCH 请求现在必须携带 `Idempotency-Key` 请求头。键必须为 16–128 个字符，只允许字母、数字、点、下划线、冒号和连字符。

处理规则：

1. 首次有效请求完成状态更新和副作用，响应包含 `replayed: false`。
2. 相同资源、相同目标状态、相同幂等键重试时返回原审批结果，响应包含 `replayed: true`。
3. 同一资源使用不同键竞争时，只有第一个请求成功，其他请求返回 HTTP 409。
4. 同一键用于其他订单或提现时，由数据库唯一索引拒绝并返回 HTTP 409。
5. 同一键不能把已经确定的结果从 rejected 改为 completed，或反向改写。
6. 缺少或格式非法的幂等键返回 HTTP 400。

后台前端为每个资源和动作生成稳定键：

- 订单：`order:<orderId>:<action>:v1`
- 提现：`withdraw:<withdrawalId>:<status>:v1`

因此网络重试或重复点击会使用同一个键，并由服务端识别为安全重放。

## 数据模型

`orders` 和 `withdrawals` 均新增：

- `decision_key`：持久化审批幂等键。
- `decision_at`：首次完成审批的时间。
- `decision_by_user_id`：执行首次审批的管理员用户 ID。

新增部分唯一索引：

```sql
CREATE UNIQUE INDEX idx_orders_decision_key
ON orders(decision_key) WHERE decision_key IS NOT NULL;

CREATE UNIQUE INDEX idx_withdrawals_decision_key
ON withdrawals(decision_key) WHERE decision_key IS NOT NULL;
```

继续保留并验证以下业务唯一约束：

- 每个用户对同一产品最多一条订单。
- 同一链上 TXID 最多绑定一条非免费订单。
- 每个用户最多一条 pending 提现。

## 提现审批实现

提现审批使用 `transaction(...).immediate()`，并在同一事务中执行：

```sql
UPDATE withdrawals
SET status = ?,
    decision_key = ?,
    decision_at = CURRENT_TIMESTAMP,
    decision_by_user_id = ?
WHERE id = ?
  AND status = 'pending'
  AND decision_key IS NULL;
```

- 只有更新行数为 1 的请求获得首次处理权。
- rejected 的余额退款只在该请求获得处理权后执行。
- 状态更新、审批键写入和退款处在同一个数据库事务内。
- 退款账户不存在、幂等键冲突或任何 SQL 失败时，状态和余额同时回滚。
- completed 不执行退款，只记录唯一状态转换。

## 订单审批实现

- 历史 pending 订单的 reject 使用立即事务、条件更新和持久化幂等键。
- 相同键重试返回安全重放，不重复改变状态。
- 不同键并发只有一个请求成功。
- NQ-P0-008 关闭的付费 approve 仍保持关闭；所有 approve 请求返回 HTTP 503，不改变订单、不写入结算时间，也不增加创作者余额。
- 重新开放真实支付后，支付回调必须继续使用 `decision_key`、支付事件唯一键和账本事务，不得恢复人工 TXID 批准。
