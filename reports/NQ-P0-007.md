# NQ-P0-007 提现路由与资金状态回归报告

完成日期：2026-09-22  
结论：**已完成并通过验收**

## 任务目标

统一提现接口为 `/api/withdraw`，确保用户提交、余额扣减、管理员批准、管理员驳回退款以及重复审批均由服务端 Session 和数据库事务保护。

## 修复前状态

- 前端调用 `/api/withdraw`，后端文件却位于 `app/api/withraw/route.js`，实际请求返回 404。
- 待处理申请检查发生在事务外，并发请求存在检查后同时扣款的时间窗口。
- 审批先读取状态再更新，更新语句没有 `status = 'pending'` 条件，两个审批请求可能重复处理同一申请。
- 驳回时状态更新和退款虽在普通事务内，但未检查条件更新结果，也未检查收款用户是否仍存在。
- 接口把内部异常文本直接返回客户端。
- 前端提交客户端保存的 `username` 和 `balance`，增加了错误信任客户端数据的风险。

## 已实施修复

### 1. 路由统一

- 新增唯一正式路由 `app/api/withdraw/route.js`。
- 删除旧的 `app/api/withraw/route.js` 及空目录。
- 前端用户页和后台页统一调用 `/api/withdraw`。
- 生产构建路由表只包含 `/api/withdraw`，旧 `/api/withraw` 实测返回 404。

### 2. 用户提交与余额扣减

- POST 必须具有有效服务端 Session，用户身份只取自 HttpOnly Cookie 对应的数据库用户。
- 前端只提交钱包地址；默认提现金额由服务端在事务中读取最新余额。
- 地址限制为 10–200 个字符且不能包含空白字符。
- 显式金额必须是有限数值且不低于 100 USD。
- 使用 `better-sqlite3` 的 `transaction(...).immediate()` 串行化写入竞争。
- 在同一事务中重新读取账户、检查 pending 申请、执行带余额条件的扣款并创建提现单。
- 扣款使用 `UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?`；余额不足时不创建提现单。
- 成功创建返回 HTTP 201，并返回服务端生成的提现 ID 和实际金额。

### 3. 重复申请保护

- 新增 SQLite 部分唯一索引：

  ```sql
  CREATE UNIQUE INDEX idx_withdrawals_one_pending_per_user
  ON withdrawals(username) WHERE status = 'pending';
  ```

- 业务检查与数据库唯一约束形成双层保护，每个用户名最多存在一笔 pending 提现。
- 重复申请返回 HTTP 409，不再次扣减余额。

### 4. 管理员批准与驳回退款

- PATCH 要求有效 Session 且角色必须为 `admin`。
- 只接受 `completed` 或 `rejected` 两个目标状态。
- 审批使用立即事务，并通过以下条件更新夺取唯一处理权：

  ```sql
  UPDATE withdrawals
  SET status = ?
  WHERE id = ? AND status = 'pending'
  ```

- 更新行数不是 1 时返回 HTTP 409，因此已处理申请不能再次批准、驳回或改变最终状态。
- 驳回只在条件更新成功后退款；退款用户不存在时抛出错误，整个事务回滚，申请保持 pending。
- 批准只更新状态，不改变已经冻结的余额。

### 5. 前端反馈

- 用户页不再发送可伪造的用户名和客户端余额。
- 管理后台读取 PATCH 响应，仅在服务端确认成功后显示成功提示；409/其他错误显示服务端业务提示。

### 6. 关联会话修正

回归时发现 `session_version = 0` 会被 `|| 1` 转换为 1，从而绕过会话版本比较。本次将其改为严格整数相等校验；伪造的版本 0 Cookie 已实测返回 401。
