# NQ-P2-002 修复报告：Nexus Verification 策略可信度体系

完成日期：2026-09-27  
状态：已完成代码、隔离数据测试、生产构建和现有数据库迁移验证。

## 问题

此前“指标已审核”“截图已通过”“HTML 已解析”分散在不同位置，没有统一等级、有效期和变更历史。用户无法快速区分开发者自报、管理员看图、报告一致性、可复现回测、平台复跑和实盘观察；管理员也可能在缺少基础材料时直接展示高可信徽章。

## 验收标准

1. 认证等级有固定顺序和明确证据边界。
2. 基础等级只能由已审核证据自动产生，不能由客户端自报。
3. 高级等级只能由管理员授予，并对每一级证据使用服务端 Schema 校验。
4. 缺少截图或 MT5 报告时不能授予高级认证。
5. 认证撤销、降级、过期和重复同步不丢失历史。
6. 公开市场只显示当前有效等级和经过裁剪的证据信息；私有摘要不泄漏。
7. 实盘认证至少观察 30 天、只允许只读连接，并设置 30 天有效期。

## 已完成修复

### 1. 六级认证模型

固定等级为：

1. `unverified`：未认证
2. `screenshot_reviewed`：设置、统计、净值三类截图均经管理员通过
3. `report_verified`：上述截图通过，且存在已解析 MT5 HTML 原始报告
4. `reproducible_backtest`：登记参数文件 SHA-256、数据集、终端版本和回测区间
5. `platform_rerun`：额外登记平台复跑编号、结果 SHA-256、运行环境和复跑时间
6. `live_verified`：登记只读提供方、脱敏账号、观察天数、最后核验日期和最大回撤

前两种可信基础等级由服务端根据现有证据自动推导。后三种等级要求管理员 Session，并且必须先达到 `report_verified`。

### 2. 数据库和不可丢失历史

新增 `strategy_verifications` 保存每个产品当前等级、状态、证据、审核人、核验时间、有效期及撤销原因；新增 `strategy_verification_history` 保存自动授予、人工批准、撤销和降级记录。两表均以稳定的 `product_id` 外键关联产品，产品删除时级联清理。

高级有效认证不会被普通自动同步覆盖；实盘认证过期后，公开 DTO 立即返回 `unverified`。再次同步会依据仍有效的截图和报告回落到 `report_verified`，同时保留先前实盘记录用于后台审计。

### 3. 服务端门禁和 Schema

新增 `/api/verifications`：

- `GET`：活动产品可公开读取当前有效认证；管理员可读取完整证据和最近 100 条历史。
- `PATCH`：只允许管理员批准或撤销认证，统一接受 JSON，并经过现有 CSRF/Origin Proxy。
- 非活动产品不能获得高级认证。
- 可复现和平台复跑要求两个 64 位 SHA-256；实盘必须是 `read_only`，观察期至少 30 天，最大回撤限制在 0–100%。
- 每次操作写入结构化安全审计；内部异常不返回数据库细节。

### 4. 产品审核联动

管理员把产品从待审改为活动状态后，同一数据库事务调用自动认证同步。只有设置、统计、净值三类必需证据全部通过才产生截图等级；再有已解析 HTML 报告才达到报告等级。管理员列表和公开产品 DTO 都返回统一认证对象。

### 5. 前台披露与后台管理

市场详情显示当前等级、核验时间和该等级的证据边界。实盘等级展示提供方、脱敏账号及只读观察天数，并明确认证会到期且不代表未来收益。公开响应仅给出报告摘要前缀和非敏感字段。

后台产品审核页显示当前等级，可授予三个高级等级或输入原因撤销。服务端会再次校验，因此修改浏览器请求不能绕过认证前置条件。

## 边界与后续事项

- `report_verified` 证明上传材料之间的一致性和可追溯性，不能证明开发者没有伪造 MT5 报告。
- `reproducible_backtest` 当前记录可复现条件，尚未由平台实际执行；平台真正复跑后才可授予 `platform_rerun`。
- `live_verified` 当前是管理员登记的只读观察证明。未来接入经纪商/监控提供方 API 后，应改为定时拉取并自动续期或降级。
- 当前后台用结构化 JSON 输入高级证据，服务端安全门禁已完成；可在 P3 管理界面拆分时改成专用表单以减少管理员输入错误。
- 认证不会构成收益承诺、独立财务审计或资金安全担保。
