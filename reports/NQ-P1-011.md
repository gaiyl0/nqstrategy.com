# NQ-P1-011 核心关系外键与删除约束修复报告

日期：2026-09-28  
状态：已完成，等待用户验收

## 原问题

数据库虽然已经把大部分身份关系迁移到稳定 `user_id`，但 `comments.post_id` 和 `orders.product_id` 仍只是普通整数。应用代码能够查询这些关系，SQLite 却不能阻止孤儿评论、指向不存在产品的订单，或产品删除后订单失去商品身份。

这对订单尤其危险：订单、许可证、下载记录和钱包流水属于历史审计链，产品下架不能等同于删除其身份。

## 验收标准

1. 审计核心实体的全部关系字段；
2. 补齐缺失的数据库外键；
3. 每个关系明确采用 `RESTRICT`、`CASCADE` 或 `SET NULL`；
4. 已有孤儿数据必须令迁移失败，不能被静默删除或改写；
5. 迁移保留现有主键和业务数据；
6. 删除父记录时，审计关系受保护，纯从属数据按设计清理；
7. 实际数据库无外键违规，完整业务回归与生产构建通过。

## 关系审计结论

本次读取实际 SQLite schema，并对所有已声明外键执行 `PRAGMA foreign_key_list` 和 `PRAGMA foreign_key_check`。关系按数据语义归为三类：

| 策略 | 适用关系 | 目的 |
|---|---|---|
| `RESTRICT` | 用户到产品、帖子、评论、订单、提现、账本；产品到订单、版本、许可证、下载；订单到许可证、下载、账本；审核人与历史记录 | 保留资金、身份、授权和审核链，存在历史时禁止删除父实体 |
| `CASCADE` | 帖子到评论/浏览事件；产品到指标、证据、报告、认证；用户或产品到收藏/关注/评分；上传所有者到未独立成账的上传记录 | 父实体合法删除时清理无独立审计价值的从属数据 |
| `SET NULL` | 用户到审计日志；产品到上传附件反向引用 | 保留日志或上传记录，同时允许非关键显示关系失效 |

旧的 `username`、`author` 等文本字段继续作为历史显示快照和兼容字段，不承担授权或所有权关联；稳定关系由对应的 `*_user_id` 外键承担。

审计发现的两个缺口：

| 子表字段 | 父表字段 | 修复前 | 修复后 |
|---|---|---|---|
| `comments.post_id` | `posts.id` | 无数据库约束 | `ON DELETE CASCADE` |
| `orders.product_id` | `products.id` | 无数据库约束 | `ON DELETE RESTRICT` |

## 迁移 002

新增 `migrations/002-relational-integrity.mjs`，版本信息：

```text
version:  2
name:     relational-integrity
checksum: 5f7a54640dcd1b7650a1d3655c6c965ee8d2088e27f1abcc76d4456464b8aa6d
```

SQLite 不能直接给已有列追加外键，因此迁移在一个 `BEGIN IMMEDIATE` 事务中重建 `comments` 和 `orders`。步骤为：

1. 统计两个关系中的孤儿行；
2. 任一计数非零时抛出 `ORPHAN_COMMENTS_FOUND` 或 `ORPHAN_ORDERS_FOUND`；
3. 建立带外键的新表；
4. 原样复制全部列；
5. 替换旧表并恢复索引；
6. 在写入迁移历史和提交事务前执行全库 `PRAGMA foreign_key_check`；
7. 发现任何违规时回滚整个版本。

迁移不会用 `DELETE`、默认父记录、空值替换或自动修复来隐藏孤儿数据。

## 迁移运行器补强

`lib/migrations.js` 现在支持迁移显式声明 `requiresForeignKeysOff`。运行器只在表重建期间对当前连接关闭外键，并在事务提交前检查全库关系，最后无论成功或失败都恢复 `foreign_keys=ON`。

生产 Next.js 服务从 bundle 内的迁移清单校验数据库历史，不在运行时混读工作目录里的迁移源码。迁移 CLI、开发和测试仍计算源码 SHA-256；部署顺序要求在构建前执行 `npm run db:migrate -- verify`。这修复了旧 `.next` 产物与新源码并存时可能产生的错误混合校验。

## 删除行为

### 帖子与评论

删除帖子会在同一数据库操作中级联删除评论。测试先建立帖子和评论，删除帖子后确认评论为零，不会留下无法访问的孤儿评论。

### 产品与订单

任何订单，包括待处理、拒绝或完成订单，都会阻止产品物理删除。`DELETE /api/products` 同步改为检查全部订单，并提示管理员使用下架保留财务审计历史。

数据库外键是最终防线：即使绕过 API 直接执行产品删除，SQLite 也返回约束错误。产品下架仍通过状态字段完成。

## 残余边界

- SQLite 外键只保护同一个数据库文件。未来拆分服务或迁移 PostgreSQL 时必须在目标数据库重新声明并验证约束。
- `CASCADE` 会真实删除从属数据，后台应继续通过业务状态执行内容隐藏、策略下架和用户匿名化；物理删除只能用于明确允许清理的父实体。
- 历史文本快照可能保留旧用户名，这是审计显示信息，不作为身份判断依据。
- 真实付费能力继续关闭。外键和订单幂等不能代替链上支付真实性核验、确认数、金额核对和资金对账；正式上线真实资金前必须再次提醒并完成该项。
