# NQ-P1-010 正式数据库迁移系统修复报告

日期：2026-09-28
状态：已完成，等待用户验收

## 原问题

`lib/db.js` 原先在每次导入时执行约 670 行建表、索引、触发器、零散 `ALTER TABLE` 和数据回填。系统虽然使用 `IF NOT EXISTS`、异常吞掉和 settings 标记维持兼容，但无法回答以下关键问题：

- 当前数据库究竟处于哪个结构版本；
- 某个迁移是否完整执行过；
- 已执行迁移代码是否被事后修改；
- 两个进程同时启动会不会重复回填；
- 中间语句失败后哪些改动需要恢复；
- 部署前是否创建了数据库一致性备份；
- 生产代码和数据库版本不匹配时是否会失败关闭。

## 验收标准

1. 有连续、唯一、不可跳号的迁移版本和名称；
2. 数据库保存迁移版本、校验和、执行时间和应用时间；
3. 已应用迁移文件修改后立即拒绝运行；
4. 每个版本在单独的立即事务内执行，失败完整回滚；
5. 两个进程并发执行不会重复迁移；
6. 重复启动不重复运行已完成迁移；
7. 现有数据库可以安全接管，不丢失已有迁移标记和业务数据；
8. 正式生产环境存在待迁移版本时拒绝启动；
9. 提供状态、执行、验证、校验和命令；
10. 执行迁移前自动创建 SQLite 在线备份；
11. 有新增迁移和恢复文档；
12. 全量测试、Lint、数据库检查与生产构建通过。

## 架构变化

### 迁移历史表

新增 `schema_migrations`：

```sql
CREATE TABLE schema_migrations (
  version INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  checksum TEXT NOT NULL,
  applied_at INTEGER NOT NULL,
  execution_ms INTEGER NOT NULL CHECK(execution_ms >= 0)
);
```

当前实际数据库状态：

```text
version:      1
name:         legacy-current-schema
checksum:     79f2e6fa291d9862baaa5663e96b13726da7f8aa09e600b33619f25e93944f7e
current:      1/1
pending:      none
```

### 001 基线迁移

原 `lib/db.js` 中的结构创建、旧字段兼容、验证码表升级、密码格式升级、角色规范化、稳定 user_id 回填、版本快照、永久授权回填、索引和触发器全部迁移到：

```text
migrations/001-legacy-current-schema.mjs
```

这是现有生产形状的只读历史基线。后续结构变化必须新增 `002`、`003`，不能继续修改 `001`。

`lib/db.js` 从约 701 行缩减为数据库连接、维护门控函数、SQLite pragma 和迁移入口，不再包含零散的热补丁 DDL。

### 迁移运行器

`lib/migrations.js` 负责：

- 校验版本必须从 1 连续递增；
- 校验名称格式和唯一性；
- 计算并验证迁移文件 SHA-256；
- 对照数据库历史 checksum；
- 拒绝未知已应用版本；
- 枚举 pending 版本；
- 使用 `BEGIN IMMEDIATE` 串行迁移；
- 在同一事务内执行迁移和写入历史；
- 每个版本完成后重新验证历史。

## 校验和防篡改

每个迁移文件声明固定 64 位 SHA-256。计算时只把 checksum 声明规范化为 64 个零，文件其余内容全部参与摘要。

系统比较两层：

1. 当前迁移文件实际 SHA-256 与文件内声明；
2. 文件声明与数据库 `schema_migrations` 历史记录。

相应失败代码包括：

- `MIGRATION_FILE_TAMPERED`；
- `MIGRATION_CHECKSUM_MISMATCH`；
- `MIGRATION_UNKNOWN_APPLIED_VERSION`；
- `MIGRATION_VERSION_SEQUENCE_INVALID`。

已应用迁移不能被静默编辑、删除、重命名或重排。

## 原子性与并发

每个迁移版本使用独立立即事务：

```text
BEGIN IMMEDIATE
  执行迁移 up(db)
  INSERT schema_migrations
COMMIT
```

任意一步抛错会回滚该版本的结构、数据和历史记录。早先已经成功提交的版本保留，修复后从失败版本继续。

两个进程同时迁移时，SQLite 写锁使它们串行。第二个进程获得锁后会在事务内再次读取版本记录，发现已经完成就跳过，不会重复执行。

## 生产失败关闭

生产默认：

```env
NEXUS_AUTO_MIGRATE=0
```

如果代码包含数据库尚未应用的版本，应用启动直接失败：

```text
Error: MIGRATIONS_PENDING:1
exit code: 1
```

生产推荐部署顺序：

```powershell
npm run db:migrate -- status
npm run db:migrate -- up
npm run db:migrate -- verify
npm run build
npm start
```

开发和测试数据库允许自动迁移。只有明确设置 `NEXUS_AUTO_MIGRATE=1` 时，生产模式才允许自动迁移，供受监督的单进程构建或恢复使用。

## CLI 与备份

新增命令：

```powershell
npm run db:migrate -- status
npm run db:migrate -- up
npm run db:migrate -- verify
npm run db:migrate -- checksum migrations/002-example.mjs
```

`up` 检测到已有数据库且有 pending 版本时，先通过 SQLite 在线备份 API生成一致性备份。备份成功前不会开始迁移；没有 pending 时不会重复备份。

本次实际迁移备份：

```text
backups/data.db-before-migration-v1-2026-09-28T06-19-26-006Z.db
```

实际运行结果：

```text
applied=1
current=1/1
pending=none
quick_check=ok
foreign_key_violations=0
```

再次执行 `up` 只返回 `current=1/1`，没有备份、DDL 或数据回填。

## 残余边界

- 当前仍使用单实例 SQLite；迁移锁只能协调共享同一个 SQLite 文件的进程。多主机各自持有本地数据库时不能形成共享锁。
- 001 是历史兼容基线，内部保留旧数据升级分支；它现在受 checksum 保护，未来不再修改。
- 当前没有通用 `down`。涉及身份、账本、订单和证据的数据变化通常不可安全逆转，使用验证过的在线备份恢复更可靠。
- 何时迁移 PostgreSQL 仍取决于真实写并发、数据量、故障恢复目标和多实例需求，不由本任务自动决定。
- 真实付费能力继续关闭，迁移系统不能代替支付真实性核验和资金对账。

## 结论

NQ-P1-010 已达到验收标准。数据库结构现在具有明确版本、不可篡改历史、单版本原子回滚、并发串行、重复启动幂等、生产失败关闭、迁移前备份、健康验证和书面恢复流程。后续结构修改必须新增迁移，不再向 `lib/db.js` 添加启动时热补丁。
