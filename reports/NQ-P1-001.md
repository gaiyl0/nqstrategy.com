# NQ-P1-001 服务端统一输入校验修复报告

完成日期：2026-09-22  
任务：引入 Zod 或同等服务端 schema，对金额、ID、角色、状态、文本长度、邮箱、钱包地址统一校验  
结果：✅ 已完成并通过生产接口回归

## 修复目标

修复前，各 API 分别使用 `Number()`、`String()`、长度判断和自由对象写入。相同类型在不同接口中的边界不一致，科学计数法、隐式类型转换、任意设置键和超长内容也缺少统一处理。

本次以 Zod 4.6.5 建立唯一的服务端校验模块，所有校验都发生在数据库查询或写入之前。客户端校验仍只用于交互提示，不作为安全边界。

## 统一校验模块

新增 `lib/validation.js`，集中定义以下规则：

| 类型 | 统一规则 |
|---|---|
| ID | 只接受 JavaScript 安全整数范围内的正整数，字符串必须是规范十进制；拒绝 `1e2`、`01`、负数、小数、空字符串和超大值。 |
| 金额 | 只接受有限十进制数，最多两位小数；拒绝科学计数法、`Infinity`、负余额、过多小数和超出业务上限的数值。 |
| 产品价格 | `0–1,000,000`，最多两位小数。 |
| 提现金额 | `100–1,000,000,000`，最多两位小数；不显式填写时仍由服务端使用账户余额。 |
| 角色 | 只允许 `user`、`developer`、`admin`、`banned`。 |
| 状态 | 产品只允许 `pending/active`；订单操作只允许 `approve/reject`；提现审批只允许 `completed/rejected`。 |
| 文本 | 用户名、产品标题/描述、帖子、评论、分类、策略标签、设置字段和文件名分别设置非空、最大长度与字符规则。 |
| 邮箱 | 去除首尾空白、转小写、最大 254 字符并验证标准邮箱结构。 |
| 验证码 | 只接受 6 位数字。 |
| 钱包地址 | 提现接受 EVM、TRON、BTC、Solana 常见地址结构；拒绝 EVM 零地址。后台 USDT、ETH、BTC 字段按各自链格式校验。 |
| 幂等键 | 只接受 16–128 字符的安全字符集。 |
| 上传元数据 | 文件名 1–255 字符、MIME 文本不超过 100 字符、文件大小必须是非负整数且不超过 20MB。 |

钱包校验确认的是地址语法。地址所有权、链网络、代币合约与实际到账仍必须由未来的真实支付核验层完成，不能用语法校验替代。

## 错误响应

所有 JSON 写接口现在统一使用 `parseJson()`：

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "提现金额最多保留两位小数",
  "fields": {
    "amount": "提现金额最多保留两位小数"
  }
}
```

- 非法 JSON 返回 HTTP 400 和 `INVALID_JSON`。
- schema 失败返回 HTTP 400 和 `VALIDATION_ERROR`。
- `fields` 按字段返回首个明确错误。
- 严格对象 schema 拒绝未声明字段，避免未来误把客户端字段直接写入数据库。
- Zod union 的嵌套错误会被展开，响应不再只显示模糊的 `Invalid input`。

## 接口覆盖

| 接口 | 校验范围 |
|---|---|
| `/api/auth/register` | 用户名、邮箱、密码、验证码、未知字段 |
| `/api/auth/login` | 登录账号/密码、重置邮箱/验证码/新密码、非法 JSON |
| `/api/auth/register/password` | 邮箱、验证码、新密码 |
| `/api/send-code` | 邮箱、验证码用途枚举 |
| `/api/products` | ID、价格、标题、描述、指标文本、交易品种、类型数组、上传路径、审核状态、管理范围 |
| `/api/posts` | ID、标题、正文、分类、置顶布尔值、分类查询参数 |
| `/api/comments` | ID、帖子 ID、正文、置顶布尔值 |
| `/api/orders` | 产品 ID、订单 ID、审批操作、幂等键、管理范围 |
| `/api/withdraw` | 金额、钱包地址、提现 ID、审批状态、幂等键 |
| `/api/users` | 用户 ID、角色、余额、密码、用户名、头像上传路径、操作组合 |
| `/api/settings` | 严格设置白名单、邮箱、钱包、URL、颜色、SMTP 与所有文本长度 |
| `/api/upload` | 文件名、大小和 MIME 元数据；原有扩展名、角色与分类大小限制继续生效 |
| `/api/download` | 产品 ID |

`/api/auth/me` 没有客户端输入，因此无需 body schema。

## 附带修复

- 设置保存接口从“写入任意键”改为严格白名单；管理员读取设置时也不再返回 `migration_*` 等内部数据库标记。
- 前端不再提交 `author`、订单 `username`、资料 `currentUsername` 等服务端不信任的历史字段。
- 下载和资产列表请求不再携带客户端用户名，身份继续完全取自 HttpOnly Session。
- products/orders 的 `role` 管理范围参数仅接受 `admin`。

## 回归结果

生产服务器端到端执行 40 项输入断言，结果为 **40/40 通过**：

- 非法 JSON、未知字段。
- 科学计数法 ID/金额、非规范 ID、负金额、三位小数、超限标题。
- 非法产品/订单/提现状态和非法角色。
- 空帖子、空评论、超长分类、字符串布尔值。
- 错误邮箱、错误验证码用途。
- 随意钱包字符串、EVM 零地址、低于最低提现额。
- 错误设置键、错误链地址、超长站点名称、超长文件名。
- 合法角色变更、合法设置保存、合法帖子写入、合法钱包与金额均能进入业务逻辑。
