# NQ-P1-012 用户表 Schema 收敛修复报告

日期：2026-09-28  
状态：已完成，等待用户验收

## 原问题

早期 `data.db` 的 `users` 表由旧版本创建。后来的代码虽然把新建表定义改成邮箱和密码必填、角色默认 `user`，但 SQLite 的 `CREATE TABLE IF NOT EXISTS` 不会修改已有表，零散 `ALTER TABLE` 也不能补上 `NOT NULL`、`CHECK`、默认值或列级排序规则。

修复前实际数据库仍存在以下结构漂移：

| 字段 | 实际旧结构 | 代码期望 |
|---|---|---|
| `email` | 允许 `NULL` | 必填且唯一 |
| `password` | 允许 `NULL` | 必填 |
| `role` | 允许 `NULL`，默认 `standard` | 必填，默认 `user`，限定四种角色 |
| `email_verified` | 允许 `NULL`，无布尔约束 | 必填且只能是 0/1 |
| `balance` | 允许 `NULL`，无范围/精度约束 | 非负、最多两位小数 |
| `session_version` | 只有 `NOT NULL` | 必须至少为 1 |
| `sms_verified` | 遗留未使用字段 | 当前业务不使用 |

这会造成全新数据库和历史升级数据库对同一写入产生不同结果。

## 验收标准

1. 审计实际列类型、空值、默认值、枚举和唯一性；
2. 通过正式迁移修复约束，不修改迁移 001/002；
3. 保留用户 ID、密码摘要、余额、头像、角色和会话状态；
4. 遗留非法值令迁移失败，不能静默覆盖；
5. 新数据库和升级数据库得到相同约束；
6. 恢复钱包余额写保护触发器；
7. 实际数据库健康检查、完整回归和生产构建通过。

## 迁移 003

新增 `migrations/003-users-schema-convergence.mjs`：

```text
version:  3
name:     users-schema-convergence
checksum: 54709951ac4f6cfa93a7d53e796a074ee56f0dd1b122aeacc077becbe3b40d1c
```

迁移首先逐项检查：

- 用户名、邮箱、密码是否为空；
- 角色是否属于 `user/developer/admin/banned`；
- 布尔字段是否为 0/1；
- 会话版本是否大于等于 1；
- 余额是否非负且最多两位小数；
- 用户名和邮箱是否存在大小写不敏感重复。

任何异常都会抛出带计数的错误，例如：

```text
USERS_ROLE_INVALID:1
USERS_EMAIL_REQUIRED:2
USERS_EMAIL_DUPLICATE_CASE_INSENSITIVE:1
```

异常发生时，迁移 003 不写历史，不删除记录，也不自动把未知角色改为普通用户。

## 最终用户表约束

迁移在立即事务中重建 `users`，最终规则包括：

- `username`：必填、非空、大小写不敏感唯一；
- `email`：必填、非空、大小写不敏感唯一；
- `password`：必填、非空；
- `role`：必填，默认 `user`，限定 `user/developer/admin/banned`；
- `email_verified`：必填，只允许 0/1；
- `join_date`：必填，默认当前时间；
- `balance`：必填、非负、最多两位小数；
- `session_version`：必填且至少为 1；
- `password_reset_required`：必填，只允许 0/1；
- `deleted_at`、`avatar_url`：按业务语义允许为空。

遗留且未使用的 `sms_verified` 不再复制到规范表。

## 钱包写保护

重建表会删除绑定在旧 `users` 表上的触发器，因此迁移在新表完成后恢复：

- `users_balance_block_nonzero_insert`；
- `users_balance_block_update`。

普通 SQL 不能创建非零初始余额或直接修改余额。余额初始化、调整、提现冻结和退款仍必须通过受控钱包维护上下文及不可变账本。

## 残余边界

- 本任务收敛的是身份和余额安全边界最关键的 `users` 表。其他业务表仍有若干旧列的宽松默认值，后续应按业务语义逐表审计，不能一次性盲目收紧。
- 2 个遗留产品、2 个遗留订单和 3 个遗留帖子无法确认原所有者，继续保留 `user_id=NULL`；不会按用户名重新匹配，也不会被新注册同名用户继承。
- 真实付费能力继续关闭。用户表约束和钱包写保护不能代替链上支付核验；正式上线真实资金前必须完成支付全链路验收并再次提醒。
